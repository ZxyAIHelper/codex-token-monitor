# Codex Token Monitor App Spec

## Goal

Build a low-power desktop app that monitors local Codex token usage from the user's own machine.

The app reads local Codex session logs and presents token consumption by total usage, time window, session, and tool activity. It must help identify sessions or actions that consume tokens unusually quickly.

## Scope

MVP only monitors local Codex logs.

Primary data source:

- Windows: `C:\Users\<user>\.codex\sessions`
- macOS: `~/.codex/sessions`

Remote/cloud task monitoring is out of scope for MVP.

## Supported Platforms

- Windows desktop app, packaged as `.exe`.
- macOS desktop app, packaged as `.app` or `.dmg`.

The app should be lightweight and suitable for long-running background use.

## Technical Direction

Use Tauri for the desktop app.

Recommended architecture:

- Rust backend:
  - Watches local Codex session log files.
  - Parses appended JSONL incrementally.
  - Maintains the derived SQLite cache.
  - Emits lightweight events to the UI when aggregates change.
  - Owns tray integration and background monitoring state.
- Frontend dashboard:
  - Runs inside the desktop WebView.
  - Displays summary cards, trend chart, session tables, detail views, settings, and alerts.
  - Receives already-aggregated data from the Rust backend instead of parsing raw logs in the UI.
- SQLite:
  - Stores derived cache only.
  - Avoids repeated parsing of unchanged historical logs.
  - Can be rebuilt from Codex JSONL logs.
- File monitoring:
  - Uses platform file notifications where reliable.
  - Uses periodic lightweight reconciliation as a fallback.

The app should not run a local web server for MVP.

## Core Metrics

The app must display:

- Total token consumption.
- Token consumption grouped by day.
- Token consumption grouped by hour.
- Task or session count.
- Session-level token consumption.
- Session input tokens.
- Session output tokens.
- Session cached input tokens.
- Session reasoning output tokens.
- Tool-related activity:
  - Tool call count.
  - Tool output size.
  - Tool output events that may have contributed to high token usage.

In this app, token direction means:

- Input tokens: tokens sent into the model context.
- Output tokens: tokens generated by the model.

Token accounting source:

- Total tokens are calculated by summing `last_token_usage.total_tokens` from Codex `token_count` events.
- Input tokens are calculated from `last_token_usage.input_tokens`.
- Output tokens are calculated from `last_token_usage.output_tokens`.
- Cached input tokens are shown separately from `last_token_usage.cached_input_tokens`.
- Reasoning output tokens are shown separately from `last_token_usage.reasoning_output_tokens`.
- Cached input tokens are part of input accounting and must not be double-counted into total tokens.

Tool accounting:

- Codex logs do not expose exact token usage per tool call.
- The app tracks tool call count and tool output size as risk indicators.
- Tool output size should not be labeled as exact tool token consumption.
- Large tool outputs should be treated as likely contributors to later input token growth.

## UI Direction

The main interface is a monitoring dashboard, not a spreadsheet-first analysis tool.

The dashboard should prioritize fast situational awareness:

- Current token burn.
- Recent trend.
- Active task or session count.
- Highest consuming sessions.
- Tool and image-related spikes.
- Clear visual warnings when usage is abnormal.

Main dashboard layout:

- Top status cards:
  - Today's total tokens.
  - Last 1 hour tokens.
  - Last 5 hours tokens.
  - Current task or active session count.
  - Input tokens.
  - Output tokens.
- Main chart:
  - Last 24 hours token trend.
  - Default view shows total tokens.
  - Input/output split may be shown if readable.
- Lower left panel:
  - Highest consuming sessions.
  - Sortable by total tokens, time, tool call count, and tool output size.
- Lower right panel:
  - Recent alerts.
  - Includes large tool output, large image/base64 payload, high-session usage, and high-hour usage.

Dashboard cards, charts, tables, and warnings should be clickable where useful.

Detail navigation:

- Total token cards open the matching time-window breakdown.
- Task or session count opens the session list for that time window.
- A day or hour opens sessions active during that period.
- A session opens the session detail view.
- A warning opens the event or session that caused it.

## Session View

Users can inspect a single session and see:

- Session name.
- Session id.
- Project or working directory.
- Start time.
- Last update time.
- Total tokens.
- Input tokens.
- Output tokens.
- Cached input tokens.
- Reasoning output tokens.
- Tool call count.
- Tool output size.
- Per-turn token usage when available.

Session detail layout:

- Header:
  - Session name.
  - Session id.
  - Project or working directory.
  - Start time.
  - Last update time.
  - Total tokens.
- Main detail table:
  - Per-turn token usage.
  - Input tokens.
  - Output tokens.
  - Cached input tokens.
  - Reasoning output tokens.
- Tool detail section:
  - Tool calls.
  - Tool output size.
  - Large output events.
  - Image/base64-like payload events.
- Sort controls:
  - Time.
  - Total tokens.
  - Tool output size.

## Time Views

The app supports time-based grouping:

- Daily view.
- Hourly view.
- Simple hourly trend chart for dashboard monitoring.

Time views should make it easy to answer:

- Which day consumed the most tokens?
- Which hour consumed tokens fastest?
- Which sessions were active during that spike?
- How many tasks or sessions were active in that period?

MVP charts should stay simple:

- Hourly token trend as a bar or line chart.
- Optional split between input and output tokens if it remains readable.
- Tables remain the source of detailed values.
- No complex chart editing, export, or custom visualization builder in MVP.

## Sorting And Filtering

Tables should support sorting by:

- Time.
- Total token count.
- Input tokens.
- Output tokens.
- Tool call count.
- Tool output size.
- Session size or log size.
- Last updated time.

Filtering requirements are not finalized yet.

## Low Power Requirements

The app should avoid repeatedly scanning all historical logs.

Preferred behavior:

- Track modified session files.
- Parse only new appended JSONL lines where possible.
- Cache parsed aggregates locally.
- Refresh the UI only when data changes.
- Fall back to periodic lightweight reconciliation to avoid missed file events.

Derived cache:

- Store parsed summaries in a small local SQLite database.
- Record each session file path, file size, modified time, and last parsed byte offset.
- Avoid reparsing unchanged historical files.
- Store aggregate rows for sessions, hourly buckets, daily buckets, tool events, and warning events.
- The SQLite cache is derived data only; Codex JSONL logs remain the source of truth.
- If cache data is missing or stale, the app can rebuild it from local Codex logs.

Initial scan:

- Default first-run scan range is the most recent 30 days.
- Settings may allow 7 days, 30 days, or all local history.
- After initial scan, the app continues monitoring newly changed session files.

## Startup And Background Behavior

The app starts as a tray-resident background monitor by default.

Default behavior:

- Launch into the system tray without opening the main window.
- Continue monitoring while the tray process is running.
- Open the main window from the tray menu.
- Provide tray actions for opening the dashboard, pausing or resuming monitoring, and quitting the app.
- Show compact token status from the tray when supported by the platform.

Tray status should include:

- Input token rate or recent input token total.
- Output token rate or recent output token total.
- Current task or active session count.
- Today's total token usage if space allows.

Tray tooltip target format:

- `In 1.2M / Out 18K / Tasks 3 / Today 1.4M`

Tray menu:

- Open dashboard.
- Pause or resume monitoring.
- Today's summary.
- Quit.

## Settings

MVP settings:

- Codex data directory:
  - Default auto-detects `~/.codex`.
  - User can override the directory if needed.
- Historical scan range:
  - 7 days.
  - 30 days.
  - All local history.
- Start at login:
  - Optional toggle.

Alert threshold editing is not included in MVP. The app uses the default thresholds defined in this spec.

## Alerts And Diagnostics

MVP should mark potentially expensive behavior:

- Very large tool output.
- High tool call count.
- Large image/base64-like content in session logs.
- Sessions with unusually high token consumption.
- Hours with unusually high token consumption.

Default alert thresholds:

- Hourly total tokens:
  - Warning: over 1,000,000 tokens.
  - Critical: over 3,000,000 tokens.
- Session total tokens:
  - Warning: over 3,000,000 tokens.
  - Critical: over 10,000,000 tokens.
- Single tool output:
  - Warning: over 50 KB.
  - Critical: over 200 KB.
- Image or base64-like payload:
  - Warning: over 100 KB.
  - Critical: over 500 KB.

## Non-Goals For MVP

- No remote/cloud usage monitoring.
- No billing integration.
- No model price estimation unless added later.
- No CSV, JSON, Markdown, or other report export in MVP.
- No modification of Codex logs.
- No interception of Codex requests.
- No dependency on Codex plugin UI.
